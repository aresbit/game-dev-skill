# 案例校准：littleprince.dev（Unity 6 + URP + WebGPU）

本流水线的其余文档是**方法**；这一份是**真实终点样本的实测数字**。

样本：`https://littleprince.dev/`《小王子·星辰之旅》——一个已发布的商业 Unity Web 构建。
原始材料（报告、37 个 WGSL 源码首变体、材质参数表、提取脚本、哈希清单）在
`case-study/littleprince-webgpu/`。下面每一条都能在那份材料里对到证据。

**为什么它值得进流水线**：它证明了「策划 → 资产 → 场景 → 可玩构建」这条链能产出真实商业作品，
而且留下了可测量的规模、参数与架构。用它来校准你的判断，而不是凭感觉。

## 1. 规模基线（用来校准预算与工期直觉）

| 项 | 实测 | 含义 |
|---|---:|---|
| 自有 C# 类型 | **275**，分布在 12 个命名空间 | 一个剧情向 3D 游戏的玩法代码量级 |
| 自有着色器 | **37** | 每一类效果单独一个，复用的极少 |
| 材质 | **90** | 37 个着色器撑起 90 个材质 = 参数驱动，不是一人一着色器 |
| Texture2D | **146**，尺寸多在 **216–512px** | 见下方"贴图尺码" |
| 主场景 `B612_Main` | 1,924 GameObject / 1,003 MeshRenderer / 416 LODGroup / 353 MeshCollider | 单场景上限参考 |
| 渲染设置 | 4× MSAA、2 级阴影级联、阴影距离 **40 m**、HDR | Web 端敢开这个档，是因为走 WebGPU |
| 场景数 | 9 + 1 bootstrap | 分章结构 |
| 语言 | 8（en/fr/es/de/pt/zh/ja/ko） | i18n 从第一天就在 |
| 代码体积 | wasm **51.77 MB** / data **39 MB** / framework.js 482 KB | Web 交付的重量级 |
| 加载单元 | catalog 里 **228 个 bundle** | 分章按需，不是一次性全下 |

**贴图尺码**（这条最反直觉）：`Sky_Hdri_Day_Cloud` 512×128、`Water_NormalA/B` 256×256、
`Steam_Sheet_SixWayNeg` 512×512、`B612_GrassTint` 216×216。只有天空 HDRI 是
8192×2048 全景（作者附了 `prepare_hdri.py` 转换脚本）。
→ 本技能 `asset_budget_check.py` 的默认 `texture_max_px: 2048` **被实证支持**：
除天空全景外，没有一张常规贴图超过 512。**不要因为生图模型能出 4K 就出 4K。**

> 诚实的缺口：本材料**没有 dump 网格数据**，所以三角面预算无法从这里校准。
> `asset_budget_check.py` 的面数阈值仍是估计值——请按你的目标平台实测后再收紧。

## 3. 角色与交互的落地形态

原文段 3「角色构建」说「复杂道具交互用 IK 精修，禁止穿模/握持脱离/道具悬空」。
这份构建给出了**真实工程里它长什么样**——全部是命名清晰的独立组件，不是一个大脚本：

| 类 | 方法/字段 | 职责 |
|---|---|---|
| `FootGrounder` | 8 / 39 | 贴地：脚底对齐地形 |
| `FootfallDetector` + `ZoneFootsteps` | 4/12 | 落脚点检测 → 分区域脚步声 |
| `LocomotionProbe` | 12 / 20 | 运动状态探测 |
| `CarryClearanceProbe` | 34 / 59 | 搬着东西时的**净空检测**（防穿墙穿模） |
| `CarryProp` | 41 / 31 | 被搬运道具的状态 |
| `CarryHandIK` | 3 / 2 | 手部 IK 抓握 |
| `DesertPilotFootLock` | — | 特定剧情节点的脚部锁定 |

→ 流水线的可执行版本：**贴地、净空、手部 IK 是三件独立的事，各自要写测试**。
不要用一个「角色控制器」把它们糊在一起——这个构建分开做，正是为了每件事都能单独调。

## 4. 分章流式：关卡 = 章节 = 按需加载

- 一章一个运行时装配集（`Bar.Runtime.dll`、`Desert.Runtime.dll`、`King.Runtime.dll`…），
  一章一个命名空间（`LittlePrince.Bar`、`LittlePrince.Desert`…）。
- 9 个场景 + 1 个 bootstrap（`JourneyMap`），catalog 里 228 个 bundle 按需拉。
- 加载策略（自研 JS 层，可直接照抄）：
  - **带哈希的** bundle / `.data` → `Cache-Control: immutable`（内容hash变了文件名就变，可永久缓存）
  - **无哈希的** catalog / settings → `no-store`（必须每次校验）
- **缓存身份陷阱**：Unity 的 IndexedDB 库名是 `UnityCache_<companyName>_<productName>`。
  这个构建把 `productName` 冻结在 `"小王子"`（页面标题后来改成了「小王子：星辰之旅」但没动它），
  并用一个锚定在「八章包发版那天」的 `CACHE_VERSION = "0.1.0+4a120fa1"` 当 `productVersion`——
  因为 Unity 的 `cleanUpCache` 会驱逐 `version != productVersion` 的条目。
  → **改 productName 或随意改版本号 = 让所有老玩家的缓存全部失效重下。**

## 6. WebGPU 的真实门槛

该站**没有 WebGL2 回退**——`navigator.gpu` 不存在就直接拒绝启动，还额外用
`requestAdapter()` 探一次，因为「有 `navigator.gpu` 不代表能用」。

为什么非要 WebGPU：**只有 compute 相关的效果才需要它**——GPU 粒子 / VFX Graph、
体积雾、GPU 剔除（本例的 `B612VegetationCull` compute 着色器）、GPU-driven 渲染。
其余（HDRI 天空、程序化天空、水、2.5D 云层）URP 在 WebGL2 上也能做。

→ 判据：**先问「有没有一步必须 compute」**。没有，就老老实实 WebGL2 + 回退；
有，再上 WebGPU，且**必须保留回退路径**（本例没保留，是它的取舍，不是你的模板）。
另注意 WebGPU 要求安全上下文（HTTPS），纯 HTTP / `file://` 会静默退回 WebGL2。

## 7. 逆向暴露的工程陷阱（段 4/5 直接用）

1. **扩展名会说谎**。`code.wasm.br` **不是** brotli——头八字节是 `00 61 73 6d`（裸 wasm）。
   `sharedassets0.resource` 不是 Unity 序列化文件，是 MP4 片段。
   → 交付前按**magic number** 校验每类资产，不要按扩展名。
2. **下载会静默截断**。5 个 60–171 MB 的关卡 bundle 经代理返回 `HTTP 502 CONNECT tunnel failed`，
   拿到的是残缺文件；有一个重试 8 次仍损坏。
   → 大资产下载后必须**校验能否解析**（不是只看 HTTP 200），并记录重试次数。
3. **Brotli 之后的长度会骗到读取器**。浏览器已经解完 brotli，但 Unity 的读取器会按压缩尺寸
   再分配一块约 2× 的缓冲区。本例自研 fetch 包装把 `Content-Length` 改写为**精确解码长度**并
   `delete Content-Encoding`，还逐块核对，超/欠就抛错。
4. **IL2CPP 元数据只有名字面**。方法体编进了 wasm，别向任何人承诺「能还原游戏逻辑」；
   能给出的是类型/方法/字段的签名面与字符串字面量。

## 8. 把「从构建产物反向提取」当作验收工具

本材料本身就是一套**不依赖执行者自述**的验收装置：

- 「这个着色器真的进构建了吗」→ 从 bundle 里抽得出 WGSL 文本才算进。
- 「这个材质参数真的生效了吗」→ 材质数值在 `materials.json` 里查得到才算。
- 「这个类型真的编进去了吗」→ `global-metadata.dat` 的名字表里有才算。

→ 段 5 的验收判据可以加一条：**构建产物必须能被独立提取器抽出目标资产**。
这比「agent 说它做完了」硬得多，且与段 4 的截图盲审互补——
截图管「看起来对不对」，提取管「东西在不在里面」。
